# IMP-03.07 — Perfil local de latencia de las cápsulas Linux

## Qué medían los 8,35 segundos

El 12/11/2026 se ejecutó una suma con la imagen precargada. El cronómetro empezó después de resolver su identidad, antes de invocar `execute`, y terminó después de lanzar `docker ps` para auditar la ausencia del contenedor. Dentro de `execute`, el runner ya había retirado la cápsula y consultado al motor para acreditar su ausencia. El valor histórico de 8,349 s corresponde a una sola observación. No existe una traza por fases de esa llamada. El marcador que el anfitrión detectó a los 40,37 s usó un reloj distinto e incluyó el arranque del huésped. [Medición original](../../.local/preproduction/imp-03-07/linux-aggregate-20261112/timed-sum.mjs) · [Recibo del anfitrión](../../.local/preproduction/imp-03-07/linux-aggregate-20261112/pass2-host-time.json).

## Cómo se midió

El perfil del 13/11/2026 ejecuta la misma suma con el runner de Alunza, QuickJS y la cápsula original en una VM VirtualBox local con 1 vCPU, 2048 MiB y solo loopback. Cada caso recibe un contenedor nuevo. El arnés comprueba el resultado, los controles de cgroup y la limpieza. La auditoría independiente ocurre después del retorno del runner. En las olas concurrentes se audita una vez que todas las llamadas de la ola han regresado. [Arnés del huésped](../../tests/runner/linux-latency.cjs).

| Ventana                                | Inicio y fin                                                                                                                                                                                                 |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Huésped frío                           | El anfitrión solicita el arranque con almacén vacío. El huésped inicia Docker, importa la imagen desde disco y ejecuta el primer caso.                                                                       |
| Primer uso con imagen precargada       | Se reinicia la VM con el almacén poblado. Se cronometra desde la nueva solicitud de arranque y, por separado, se mide la primera invocación dentro del huésped.                                              |
| Runner                                 | Desde la invocación con imagen fijada hasta recibir el resultado y la confirmación de limpieza. Incluye creación, inspecciones, arranque, ejecución, cierre de canales, retirada y verificación de ausencia. |
| Ventana comparable al ensayo histórico | Desde la invocación hasta que finaliza el proceso CLI de auditoría. La consulta inicial de identidad se mide aparte.                                                                                         |
| Tiempo del supervisor                  | Ventana interior del puente de confianza. Incluye la comprobación de recursos, preparación, lanzamiento del trabajador y su finalización.                                                                    |

Para atribuir el tiempo de pared, las esperas de salida y de fin de proceso se combinan por unión de intervalos. El tiempo del supervisor y la vida del contenedor se solapan con las fases del runner. El p95 usa el rango más próximo superior (48.ª de 50). El desglose de una fila p95 utiliza los intervalos de esa misma solicitud.

Las series RUN y SUBMIT de un caso usan la misma entrada para aislar el coste del ejecutor. Un control de SUBMIT añade un segundo caso oculto y requiere crear y retirar otra cápsula. La prueba de contención lanza hasta cuatro solicitudes simultáneas dentro del mismo huésped de diagnóstico. En el diseño del proveedor Linux cada solicitud dispondría de su propia VM. NestJS, la base de datos, las cuotas HTTP y el trayecto del cliente quedan fuera del cronómetro del runner. El criterio del producto incluye asignación, ejecución, limpieza, persistencia y respuesta. [RNF-REN-02](../../specs/10-calidad-y-pruebas.md).

## Prioridad de optimización

1. **Validar una VM de un solo uso que esté lista a tiempo.** El gestor tardó 28,50 s solo hasta disponer de Docker en el segundo arranque. En un host de laboratorio Linux con virtualización nativa, comparar localmente el candidato de imagen precargada con una microVM de arranque rápido o una VM virgen ya lista que se asigna una sola vez. Registrar por separado disponibilidad, asignación, retirada y verificación. Si se prueba capacidad precalentada, medir también su espera y conservar el TTL desde la creación. La imagen y las tareas de preparación del huésped se pueden construir antes de recibir código de un alumno. Mantener una cápsula limpia y comprobada por caso. [Contrato de vida y limpieza](IMP-03-ejecutor-linux-plan.md).
2. **Acortar el arranque de cada cápsula.** Repetir los 50 SUBMIT de dos casos con el mismo digest, límites, Docker y runtime sobre el host Linux de comparación. Instrumentar el tiempo entre la petición de arranque, el inicio del proceso y la confirmación del motor. El desglose actual mide su duración total. Si se reproduce, comparar una variante concreta de arranque local contra ese control, de una en una, y revalidar memoria agregada de 128 MiB, descendientes, estado limpio y controles de red. Registrar por separado el arranque del trabajador, la inicialización de QuickJS y la recepción final para elegir el siguiente tramo si persiste la brecha.
3. **Usar el SUBMIT de dos casos para decidir si avanzar.** Con las otras fases fijas, un modelo que descuenta el 50 % del `start` de cada envío y vuelve a ordenar las 50 muestras deja un p95 de **5,662 s**. Descontar el 75 % lo deja en **4,640 s**, con 0,360 s nominales hasta 5 s para el resto del recorrido. Llegar a menos de 5 s solo en el runner exigiría recortar más del **66,2 %** de ambos arranques bajo ese supuesto. Son estimaciones contrafactuales. Para validar una mejora cuentan los tiempos medidos del cliente e inventario final, con errores incluidos. Repetir la comparación en concurrencia con un huésped virgen por solicitud. [Agregador y cálculo por muestra](../../tests/runner/linux-latency-report.cjs).

Los tres arranques acumularon 256 solicitudes, con 62 diagnósticos de plazo y limpieza confirmada en las 256. Al concluir cada arranque se verificaron cero contenedores. Se retiró la VM y los siete archivos de disco propios. El inventario de máquinas, discos y máquinas en ejecución al cierre coincidió con el inicial. La campaña no usó Docker Desktop del usuario ni servicios remotos. [Recibo de retirada](../../.local/preproduction/imp-03-07/linux-latency-20261113/guest-retirement.json).

## Del arranque de cada cápsula a la entrega del resultado

El ensayo usa el mismo huésped persistente, la imagen precargada y el mismo SUBMIT sintético de dos casos. Se cronometra `execute` dentro del huésped. La consulta independiente que comprueba la ausencia de contenedores queda fuera del cronómetro. El reloj monotónico del proceso lector marca la petición de arranque, la respuesta HTTP 204 de Docker y la llegada de la última trama de stdout del puente. La última marca cuenta como entrega solo si el supervisor puede leer el paquete completo y validar su esquema. Después de recibirlo, el runner todavía espera el cierre de los canales, confirma el estado del proceso, elimina el contenedor y comprueba su ausencia. El tiempo que reporta el puente para su trabajador se superpone con parte de esos tramos e incluye su inicialización. [Instrumentación y reproducción](../../.local/preproduction/imp-03-07/general-vbox-result-profile/README.md).

El primer SUBMIT, medido por separado, aprobó en 10,119 s. En los siguientes 50 envíos secuenciales aprobaron los 100 casos. El runner tardó **5,770 s de mediana y 6,455 s de p95**. Ninguno terminó antes de 5 s. En las 102 cápsulas, incluidas las de calentamiento, se verificaron los cuatro controles de recursos. Al terminar, el inventario filtrado por los 51 identificadores de ejecución encontró cero contenedores. El ensayo usó el socket de Docker de `Laboratorio-Ubuntu`. [Observaciones originales](../../.local/preproduction/imp-03-07/general-vbox-result-profile/samples.jsonl).

| Inicio del intervalo hasta recibir el resultado           | Visible · mediana | Visible · p95 | Oculta · mediana | Oculta · p95 |
| --------------------------------------------------------- | ----------------: | ------------: | ---------------: | -----------: |
| El runner solicita arrancar la cápsula                    |           1,839 s |       2,180 s |          1,768 s |      2,346 s |
| Marca de arranque que registra Docker (`State.StartedAt`) |           1,759 s |   **2,097 s** |          1,695 s |  **2,191 s** |
| El runner recibe la confirmación de arranque de Docker    |           0,961 s |       1,176 s |          0,892 s |      1,176 s |

Cada columna se calcula con sus 50 observaciones. La marca registrada por Docker usa el reloj civil del huésped, calibrado contra el reloj monotónico antes y después de cada envío. La mayor variación observada del desfase fue 0,956 ms, con las 50 muestras dentro del criterio de 5 ms. La llegada del paquete y el HTTP 204 usan directamente el mismo reloj monotónico. En [Docker 29.1.3](https://github.com/moby/moby/blob/docker-v29.1.3/daemon/start.go#L208-L234), el motor toma el valor de `StartedAt` antes de solicitar la creación de la tarea: esa fila no mide la entrada al ejecutable. [Distribuciones y calibración](../../.local/preproduction/imp-03-07/general-vbox-analysis/summary.json).

La solicitud 37 ocupó el rango 48 de las 50. Sumando sus dos casos, consumió **0,728 s** hasta pedir los arranques (incluida la creación de los contenedores), **1,956 s** esperando su confirmación, **2,213 s** entre la confirmación y los paquetes, **1,375 s** desde los paquetes hasta que el runner pudo leerlos tras la salida y **0,181 s** en inspección, limpieza y retorno. El resto de la solicitud sumó 0,001 s. De los 2,213 s hasta recibir los paquetes, el puente cronometró 1,927 s de trabajo interno, que abarca preparación, lanzamiento de Node, uso de QuickJS y cierre del trabajador.

**Primer experimento recomendado.** Comparar el flujo actual con dos cápsulas vírgenes preparadas para un solo SUBMIT, arrancadas con el canal de entrada abierto y sin datos del estudiante. Asignar los casos en orden, conservar el límite agregado de 3 s y los 128 MiB por cápsula, y confirmar salida y limpieza antes de responder. Medir también lo que espera una solicitud cuando falta una cápsula lista y el coste de reponerlas. La comprobación debe incluir los fallos además de los aciertos.

Si se reduce en cada observación el tiempo medido de creación y arranque, y se reordenan las 50 duraciones manteniendo los demás costes, una reducción del 50 % deja un p95 estimado de **5,127 s**. Al 75 %, el modelo da **4,464 s**. La frontera de 5 s corresponde a una reducción del 54,8 % de ese tramo. Adelantar por completo la creación y el arranque de la oculta únicamente daría 5,276 s. Son estimaciones del runner; hacen falta una prueba de la variante y una medición de extremo a extremo para conocer la mejora real y el margen disponible para la API. [Cálculo reproducible](../../.local/preproduction/imp-03-07/general-vbox-analysis/summarize.py).

## Comparación con dos cápsulas de un solo uso ya arrancadas

Se compararon dos maneras de atender el mismo SUBMIT de dos casos en `Laboratorio-Ubuntu`. En el control, el runner crea y arranca una cápsula cuando llega el turno de cada caso. En la variante, el supervisor prepara dos cápsulas en paralelo, comprueba que Docker las ha arrancado y mantiene abiertos sus canales. Al asignar un caso, comprueba la identidad y que la cápsula sigue en ejecución antes de enviarle datos. El supervisor original ejecuta primero el caso visible y después el oculto con el presupuesto restante. La reserva admite una sola pareja. La reposición comienza una vez retirados los contenedores de la solicitud anterior. [Candidato experimental](../../.local/preproduction/imp-03-07/vbox-warm-ab/candidate/pair.mjs).

El perfil se fijó antes de medir: diez bloques de cinco solicitudes por modo, alternando qué modo se prueba primero. En cada modo, 25 solicitudes llegan justo al abrirse el turno y 25 llegan seis segundos después. La primera llegada encuentra la reserva vacía. El reloj monotónico cuenta desde el instante programado de llegada hasta tener el diagnóstico, haber retirado los contenedores y verificar su ausencia mediante una consulta independiente a Docker. Incluye espera por capacidad y demora de despacho. El p95 usa la observación 48 de las 50 ordenadas e incluye errores. El perfil tiene una solicitud activa como máximo y mide el runner y la comprobación final en la VM ya encendida. ## Reposición durante el segundo caso del SUBMIT anterior

La referencia de este ensayo prepara una pareja después de confirmar la limpieza del envío anterior. La variante inicia la preparación cuando el envío en curso entra en el caso oculto. Ambos modos usan las mismas cápsulas de un solo uso. El planificador permite una pareja en servicio y una en reserva, incluida la que todavía se está preparando. Una pareja se asigna a un solo envío y recibe los datos de cada caso después de su admisión. [Políticas y calendario declarados antes de medir](../../.local/preproduction/imp-03-07/vbox-overlap-ab/campaign/design.json).

Se programaron diez bloques de cinco SUBMIT por modo, alternando el orden. En cada modo, 25 solicitudes llegan inmediatamente después del envío anterior y 25 tras una pausa de 6 s. La primera de cada bloque comienza con la reserva vacía; la última no prepara una pareja para el bloque siguiente. La métrica principal va desde la llegada programada hasta confirmar el diagnóstico y verificar que los contenedores de esa solicitud desaparecieron. Para detectar el coste sobre el envío en curso se comparan los tiempos de servicio después de obtener la pareja y los tiempos del caso oculto en las 40 posiciones con sucesor de cada modo. ## Del POST de arranque al proceso y a la respuesta de Docker

Este ensayo conserva la imagen, la pareja de cápsulas vírgenes y la reposición posterior al cierre auditado. El primer tramo comienza cuando el runner solicita el arranque y termina cuando Linux carga el ejecutable Node de la cápsula. El segundo termina cuando el runner recibe y valida el HTTP 204 de Docker. Este Node ejecuta el puente que espera la entrada: los casos y el código del estudiante se entregan después, una vez asignada la pareja. La posterior comprobación de `Running` queda fuera de ambos tramos.

La referencia de proceso es `sched_process_exec`, en una [instancia privada de ftrace con reloj monotónico](https://docs.kernel.org/trace/ftrace.html). La unión exige que el PID del evento corresponda al PID que Docker reporta en la primera inspección y que el grupo de recursos y el ejecutable correspondan a la cápsula. Se toman referencias de reloj inmediatamente antes y después de cada POST. Para distinguir etapas anteriores, también se conservan la marca civil de Docker y el [nacimiento del PID en ticks del kernel](https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html). Ninguno de estos dos valores sustituye al evento de entrada a Node.

Se observaron los 100 arranques de la serie: un único `exec` de `/usr/local/bin/node` por PID, siempre entre el POST y el HTTP 204, con cero eventos perdidos. En cada una de las 100 cápsulas pasó más tiempo antes del `exec` que después, incluso contando la incertidumbre de los relojes. La visible fue la última en quedar lista en 26 parejas y la oculta en 24.

Empezar por distinguir, dentro del tramo nacimiento → Node, cuánto tarda en quedar creada la tarea del runtime y cuánto en recibir y atender la orden que inicia el ejecutable. El perfil usa esa devolución como frontera entre el trabajo que espera del runtime y el trabajo que todavía queda en el shim. [Código de creación de la tarea en containerd 2.2.1](https://github.com/containerd/containerd/blob/v2.2.1/cmd/containerd-shim-runc-v2/process/init.go#L149-L179).

Una segunda referencia es la última salida observada del comando en el kernel. Para cada cápsula se comprueba que el ejecutable `runc` es hijo del shim y antecesor de su proceso inicial. Tras `exit_group(0)` se toma el último evento de salida de los hilos de ese grupo cuyo nombre contiene `runc`, y se contrasta con el retorno exitoso en el shim. Las sondas de la VM usan el mismo reloj monotónico. Tres marcas internas delimitan la actualización del estado cuando el proceso inicial está listo y el retorno de la preparación interna de `runc`. [Correspondencia entre sondas e instrucciones de ambos binarios](../../.local/preproduction/imp-03-07/vbox-runc-create/probe/README.md).

Empezaría por el tramo desde el nacimiento del PID hasta que el padre de `runc` comienza a guardar el estado al recibir `procReady`. Dominó en las otras 22 parejas. Guardar el estado en sí tomó 5 ms de mediana y 34 ms de p95. ## De la salida del PID al shim, containerd y Docker

Este perfil examina los 394 ms de mediana entre la salida del proceso principal y el acuse de Docker observados en el diagnóstico anterior. Son distribuciones independientes: no se suman sus medianas ni sus percentiles. La unión por ID, PID/cgroup, procesos privados y goroutine verifica el recorrido completo por cápsula. La incertidumbre máxima de conversión entre relojes fue 3,460 ms. No hubo eventos perdidos ni cápsulas sin asociar. El tramo dentro de Docker dominó en 96/100 cápsulas.

**Dónde concentrar el recorte:** la retirada sincrónica de la tarea dentro de Docker, no el transporte de `TaskExit`. `Task.Delete` tardó **330 ms de mediana / 494 ms de p95** por cápsula y representó el 71,3 % de mediana del tiempo desde salida del PID hasta `/wait`. Dentro de esa llamada se sucedieron dos operaciones: `runc.Delete` en el shim activo (**120 / 209 ms**) y `binary.Delete` del callback que limpia después de desconectarse el shim (**138 / 236 ms**). La suma de ambas operaciones en cada cápsula tuvo **271 / 412 ms**, y explicó el 80,6 % de mediana de `Task.Delete`.

La segunda operación incluye lanzar el shim auxiliar, pedir una retirada forzada de runtime, procesar su respuesta y retirar el bundle. No se midieron por separado esas fases internas. No equivale a afirmar que el segundo `runc` consuma todos los 138 ms ni que la limpieza sea redundante y pueda eliminarse. Las sondas adicionales de `route-probes-aux.json` están preparadas, pero no hay campaña auxiliar ejecutada que acredite sus resultados. [Cierre y callback de containerd](https://github.com/containerd/containerd/blob/v2.2.1/core/runtime/v2/shim.go) · [Operación del auxiliar](https://github.com/containerd/containerd/blob/v2.2.1/core/runtime/v2/binary.go).

Para recuperar **225 ms** en el modelo, haría falta recortar unos **112,5 ms efectivos por cápsula** en esas dos operaciones, o un 43,94 % de su tiempo de manera proporcional, reordenando los 50 envíos. El p95 resultante sería 5,341 s y seguiría sobre 5 s en esta corrida. Si solo se adelantara el acuse de `/wait`, sin acelerar el EOF concurrente, el ahorro modelado sería **159 ms**. Incluso eliminar idealmente ambas operaciones daría 5,101 s: hay otros costes y no se debe prometer la meta a partir de este único tramo. Las marcas sitúan el EOF después de ambas operaciones en 100/100 cápsulas, pero no demuestran que toda reducción futura se transfiera sin cambios al EOF.

La recomendación es centrar el próximo candidato en el coste real de esas dos operaciones de retirada y sus procesos auxiliares, manteniendo la limpieza completa y la verificación de ausencia. La serie todavía no acredita una opción de configuración o un cambio seguro de runtime que produzca el ahorro. No se implementó un atajo, no se omitió el callback y no se modificaron los límites ni el runner de producción.

La auditoría final del 14/11 a las 03:01:39 UTC comprobó las 104 identidades y cero procesos privados, cgroups con procesos del ensayo, montajes, dispositivos de bucle o sondas pendientes. El motor habitual conservó ID, socket e inventario. Al retomar el 15/11, VirtualBox mostraba la VM encendida, pero dos conexiones SSH no alcanzaron el banner; no fue posible comprobar de nuevo su estado interior. No se reinició ni alteró la VM. La conclusión de limpieza corresponde a la auditoría del cierre, y el análisis se completó con la evidencia guardada.
