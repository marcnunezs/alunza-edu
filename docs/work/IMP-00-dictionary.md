## Entidades y contratos

Todas las tablas viven en el esquema privado `app`, no publicado por la Data API. Los instantes son `timestamptz` UTC y los identificadores son UUID. Las fechas de creación tienen `now()` como valor inicial. Los límites de texto siguientes son supuestos técnicos revisables de esta base local, no requisitos institucionales nuevos.

La proyección implementada de `/me` contiene `id`, `displayName`, `accountState` y membresías `{organizationId,role,state}`; el correo normalizado y `user_id` permanecen internos. Los nombres de mapping adicionales de la tabla describen correspondencias del diccionario, no campos públicos ya habilitados.

| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

Las FK usan `ON DELETE RESTRICT`. No se añaden clases, invitaciones, contenido, auditoría de negocio, almacenamiento ni vectores. La unicidad por organización de membresías no impide que una identidad participe posteriormente en otro ámbito autorizado; este incremento no habilita gobierno multiinstitucional ni roles múltiples en una misma membresía.

## Permisos y contexto transaccional

`alunza_app` es un rol PostgreSQL de conexión propio, `LOGIN`, `NOINHERIT`, sin superusuario, creación de bases/roles, replicación ni `BYPASSRLS`. No es propietario de tablas. El bootstrap local asigna su contraseña por separado; el SQL versionado no contiene credenciales. Solo recibe `USAGE` sobre `app` y `SELECT` sobre las tres tablas. No se conceden escrituras ni acceso a `auth.users`.

Las tres tablas activan y fuerzan RLS. Los perfiles y membresías permiten exclusivamente filas del actor de `app.actor_id`; esto proporciona los metadatos mínimos para comprobar estado vigente incluso cuando se debe denegar la operación. Las organizaciones exigen simultáneamente `app.organization_id` coincidente, organización no archivada, perfil `ACTIVE` y membresía propia `ACTIVE`. Las políticas no se invocan recursivamente ni usan funciones `SECURITY DEFINER`.

NestJS valida el JWT antes de establecer `app.actor_id` mediante `set_config` parametrizado y local a la transacción. Comprueba el perfil y la membresía vigente antes de establecer la organización autorizada. `COMMIT` o `ROLLBACK` elimina el contexto; la integración debe verificar reutilización de una conexión sin heredar otra identidad. Un administrador no obtiene acceso a otras organizaciones ni acceso pedagógico por este rol.

`PUBLIC`, `anon`, `authenticated` y `service_role` no reciben privilegios sobre el esquema de dominio. Los privilegios administrativos usados para migraciones y fixture quedan separados del proceso web/API. No existe una política de escritura para el rol de aplicación.

## Fixture y recuperación

El proyecto CLI local se identifica como `alunza-edu-foundation`: API/Auth `15421`, PostgreSQL `15422`, shadow `15420`, Studio `15423` e Inbucket `15424`. Los puertos `54321–54324` pertenecen a otro proyecto existente y no se reutilizan; los rangos `553xx` y `563xx` resultaron reservados por Windows/WSL y se descartaron tras comprobar el fallo de bind. El emisor local configurado es `http://127.0.0.1:15421/auth/v1`; las pruebas integradas disponen de un proyecto separado en `.local/integration-workspace` con puertos `16421`, `16422`, `16420`, `16423` y `16424`, sin resetear la base de desarrollo.

`auth.enable_signup = false` bloquea el registro público. `auth.email.enable_signup = true` mantiene habilitado el proveedor de correo/contraseña para iniciar sesión con los usuarios creados por Auth Admin: en CLI 2.101.0 este campo configura `GOTRUE_EXTERNAL_EMAIL_ENABLED`. Desactivarlo impediría también el login de las cuentas del fixture. El bootstrap no envía invitaciones ni correos externos.

[El fixture incremental](../../fixtures/foundation/identity.json) conserva dos organizaciones y seis identidades ficticias: un administrador, un profesor y un estudiante por organización. IDs, nombres y correos `@alunza.test` son estables; no contiene contraseñas ni JWT. El bootstrap autorizado crea usuarios mediante Auth Admin local y persiste las relaciones. Las credenciales de acceso solo se generan en `.local/`, ignorado por Git.

Es un subconjunto de la demo DEC-012: siguen pendientes los seis estudiantes adicionales, las tres clases, los ejercicios y los documentos de la demo completa. Los negativos temporales de estado deben restaurarse y comprobar los conteos finales; no se crea un administrador global ni se altera el único administrador para eludir los casos negativos.

La migración inicial es para un entorno local vacío del proyecto. La recuperación local se realiza mediante reconstrucción explícita del entorno desechable y reaplicación de migraciones más bootstrap, después de comprobar el destino; no se ejecuta un reset automático de datos compartidos. En un entorno con datos a conservar, una corrección posterior requiere una nueva migración de avance, no editar una ya aplicada. No se define un rollback destructivo sobre `auth.users`.
